# F4: рынок одного актива

Точка входа: `marketsim.sim.api.run(config, seed, out_dir)`. Результат — каталог с шестью таблицами
и `meta.json`, который читает `marketsim.sim.log_schema.load_run`. Торговля идёт только через K1
`Gateway`; интерфейсы K1–K4 и тесты контрактов не изменены.

## Запуск

Из корня репозитория после установки `.[dev]`:

```bash
python -m marketsim.experiments.run configs/f4_pilot.yaml --out runs/f4/pilot
```

Для проверки одного прогона добавьте `--limit 1`. Каталог эксперимента должен быть новым:
готовые результаты не перезаписываются и автоматически не пропускаются. Параллельный runner
с возобновлением относится к F7. Для C++ замените `exchange_backend` на `cpp` после установки `cpp/`.

Конфиги `f4_e1.yaml`, `f4_e2.yaml`, `f4_e3.yaml` запускаются той же командой с отдельным `--out`.
В каталоге сохраняются исходная конфигурация `experiment.json`, логи и накопительная `summary.csv`.
Notebook `notebooks/03_experiments.ipynb` читает эти результаты; каталог `runs/` не коммитится.

## Границы F4

- `graph: single_asset` — явно выбранный синтетический рынок, без графа K2; тикер и стартовая цена
  находятся в `agents`. Загрузка цепочки из `pilot.yaml` относится к F5 и пока отвергается.
- `external: flat`, `use_market_index: false`. Постоянный fixture загружается через API данных;
  его постоянные уровни продолжаются на всю длину прогона. Исторические данные не нужны.
- Сессия имеет длину 1. Очередь упорядочена по времени и порядку добавления. Сначала выполняется
  открытие первой сессии, начальные котировки маркет-мейкеров и снимок; инвесторы просыпаются
  через экспоненциальные интервалы. События с `t >= n_sessions` не исполняются.
- GTD истекает событием планировщика; перед следующим решением старые заявки агента снимаются.
  Перед завершением записывается последний снимок, затем оставшиеся заявки снимаются,
  чтобы зарезервированные ресурсы вернулись владельцам.

## Параметры агентов

Неизвестные ключи и некорректные значения отвергаются до создания файлов прогона.
Полный набор значений по умолчанию — `sim/settings.py`; разрешённые параметры:

| Группа | Поля |
|---|---|
| Рынок | `ticker`, `initial_price_ticks` |
| Участники | `valuers`, `trend`, `noise`, `market_makers_per_asset`, `n_funds` |
| Ресурсы инвесторов | `concentration`, `total_cash_cents`, `total_shares` |
| Ресурсы маркет-мейкеров (на каждого) | `market_maker_cash_cents`, `market_maker_shares` |
| Сигналы | `valuation_std`, `gamma`, `trend_lookback`, `trend_scale` |
| Пробуждения | `decision_rate`, `market_maker_rate` (в среднем решений на сессию) |
| Заявки | `rho`, `threshold`, `aggressive_prob`, `protection_fraction`, `passive_offset_ticks`, `tif`, `order_lifetime` |
| Маркет-мейкер | `market_maker_spread_ticks`, `market_maker_qty`, `inventory_skew_ticks` |
| Стадность | `herding: {h, neighbors, ttl}` |
| Проверки и эксперименты | `debug`, `ablation` |

Оценщик хранит постоянную индивидуальную оценку `P0 * (1 + e)`, где `e` нормально распределена
с заданным `valuation_std` и ограничена диапазоном [-0.9, 0.9]. Трендовый агент сравнивает
текущую цену с последним снимком не позже `now - trend_lookback`; до появления такой истории
используется стартовая цена. Шумовой агент выбирает сигнал равномерно из [-1, 1].

Сеть знакомств направленная, фиксированная на прогон, без самого себя и повторных соседей.
Соседи публикуют направление итогового намерения (-1/0/+1), включая намерение, которому не хватило
ресурсов. Неопубликованный или просроченный сигнал считается нулём; знаменатель — полное число
соседей. Маркет-мейкеры в эту сеть не входят.

Сначала агент снимает старые заявки, затем получает собственный портфель и публичное состояние
рынка. Объём вычисляется по F4, ограничивается доступными ресурсами и округляется вниз.
Агрессивная заявка — IOC с защитной ценой; пассивная размещается у лучшей цены своей стороны.
Покупка округляет защитную цену вниз, продажа вверх. Средняя цена двух котировок округляется
вниз до целого тика; при пустой стороне используется последняя сделка, затем стартовая цена.

Маркет-мейкер снимает обе свои заявки и размещает новые вокруг наблюдавшейся до снятия середины.
Избыток акций относительно стартового запаса понижает обе котировки. Его деньги и акции конечны.

Фонды — фиксированная, случайно выбранная подгруппа инвесторов, а не отдельная стратегия.
При изменении C меняется только распределение денег и акций между этими фондами и остальными.
Суммы, численность групп и набор стратегий сохраняются. Остатки целочисленного деления
раздаются по возрастанию ID. Ресурсы маркет-мейкеров в C не входят.

## Воспроизводимость и проверки

`SeedSequence(seed)` создаёт отдельные потоки для групп, оценок, сети, пробуждений и решений.
У каждого агента свои потоки пробуждений и решений. Одинаковые конфиг и seed дают одинаковые
таблицы и `run_id`. Время запуска и фактическая длительность в metadata естественно различаются.
`wall_time_s` измеряет расчёт симуляции, без записи Parquet и его повторной проверки.

Сохранение денег и акций проверяется в начале и конце каждого прогона. `debug: true` добавляет
проверки после каждого решения и истечения. Начальные и конечные суммы записываются в metadata.
Данные сначала записываются во временный каталог и проверяются через `load_run`, затем
каталог переименовывается в окончательный. Существующий результат не перезаписывается.

## Ограничение статусов K1/K3

K1 не имеет кодов ручной отмены и истечения GTD, хотя K3 называет `orders.status` финальным статусом.
F4 не добавляет новые коды и не меняет контракт. В `orders.status` записывается последний статус
исполнения K1; количество исполненных акций обновляется и для пассивных заявок.
Отмена, истечение и снятие при завершении представлены событиями `order_cancelled`,
`order_expired`, `run_end_cancelled` с `order_id`, `agent`, `remaining_qty`.
Это указано и в `meta.order_status_semantics`. Для полной истории жизни заявки нужно читать
`orders` вместе с `events`. Потребителям K3 нельзя считать все строки `RESTING` активными
на конец прогона. Полноценное расширение enum требует согласования владельцев K1 и K3.

Отказы шлюза из-за ресурсов имеют `order_id = 0`; это не уникальный идентификатор строки лога.

## Протокол E0–E3, зафиксированный после пилота

Пилот E0: seeds 1–3, 30 сессий, прогрев 5, снимки через 0.02 сессии, 40 оценщиков,
20 трендовых, 20 шумовых, 1 маркет-мейкер, 8 фондов. Стадность h=0, C=0.5.
Пилот показал торговлю во всех трёх прогонах, пустую сторону в 0.16–0.72% времени после прогрева,
среднюю абсолютную ошибку относительно средней оценки 0.19–1.50%.
Проверки ресурсов выполнены; наблюдений недостаточно для вывода об исследовательских гипотезах.

Основные прогоны используют те же параметры времени и численности; seeds 1001–1030, без пересечения
с пилотом. Общие seeds разных вариантов используются для сравнения; одна единица статистики — прогон.
Протокол фиксируется до запуска основных экспериментов.

| Эксперимент | Сетка | Прогоны |
|---|---|---|
| E1 | h = 0, 0.3, 0.6; C = 0.2, 0.5, 0.8 | 270 |
| E2 | при h=0.6, C=0.5: baseline, без стадности, без трендовых | 90 |
| E3 | при h=0.3, C=0.5: спред маркет-мейкера 4, 10, 30 тиков | 90 |

В E2 `ablation: no_herding` устанавливает эффективный h=0. `ablation: no_trend` заменяет правило
трендовых агентов на шумовое, сохраняя их ID, ресурсы, принадлежность фондам и интенсивность
пробуждений. Это контроль постоянной численности, а не удаление участников рынка.

`experiments/diagnostics.py` содержит первичные диагностические сводки по K3 для F4;
метрики исследовательской валидации и их окончательные определения остаются задачей D1.
Просадка и ошибка оценки считаются по снимкам с двумя сторонами стакана; отсутствие котировок
не интерполируется в цену. Доля пустой стороны взвешена длительностью интервалов снимков.
Execution rate — доля исполненного количества для заявок, поданных после прогрева, с учётом
их последующего исполнения. Notebook показывает распределения и bootstrap по прогонам.
Показательные прогоны выбираются по ближайшей к медиане и 90-му перцентилю просадке.
30 сессий — короткий эксперимент; выводы ограничены этим горизонтом и выбранными параметрами.
