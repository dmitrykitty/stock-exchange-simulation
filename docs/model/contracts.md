# Контракты между частями проекта

Контракт — это интерфейс, через который одна часть проекта пользуется другой: сигнатуры функций, форматы файлов, имена колонок, смысл значений. Пока контракты не меняются, каждый может переписывать свою реализацию как угодно, и ничего у других не ломается. Поэтому контракты **неизменяемы без процедуры** (раздел 7).

Каждый контракт описан **в коде** (это главный источник правды) и проверяется **тестами** в `tests/contracts/`. Этот документ объясняет их словами.

| Контракт | Код | Тесты | Владелец | Потребители |
|---|---|---|---|---|
| K1 биржа и шлюз | `src/marketsim/market/api.py`, `cpp/include/lob_core/types.hpp`, `exchange.hpp` | `test_market_contract.py`, `test_gateway_contract.py` | O | S |
| Данные | `src/marketsim/data/schemas.py`, `src/marketsim/data/api.py` | `test_data_contract.py` | D1, D2 | все |
| K2 граф и внешние сигналы | `src/marketsim/graph/api.py`, схема `EXTERNAL`, `graph/reference.py` (сигнатура) | `test_graph_contract.py` | D2 | S, D1 |
| K3 лог прогона | `src/marketsim/sim/log_schema.py` | `test_config_and_log_contract.py` | S | D1, O |
| K4 конфигурация | `src/marketsim/experiments/config.py` | `test_config_and_log_contract.py` | S | все |

---

## K1. Биржа и шлюз

**Зачем:** агенты (S) торгуют, не зная, как устроен стакан; движок (O) можно переписать с Python на C++, не трогая агентов.

- `Exchange`: `submit`, `submit_batch`, `cancel`, `top`, `depth`, `last_trade`, `n_assets`. Две реализации: `PyExchange` (эталон) и `CppExchange` (обёртка над `lob_core`).
- `MarketGateway`: `place`, `cancel`, `expire`, `portfolio`, `market`, `drain_fills`, `check_invariants`. Агенты пользуются **только** шлюзом.
- Массивы: `ORDER_DTYPE`, `FILL_DTYPE`, `REPORT_DTYPE`, `DEPTH_DTYPE`. Константы: `Side`, `TimeInForce`, `Status`, `NO_PRICE`, `CONTRACT_VERSION`.
- Полная семантика (единицы, сопоставление, self-trade, статусы, резервирование, примеры): `docs/plans/phases/F3_exchange_engine.md`, раздел 2.

## Данные

**Зачем:** все читают данные одинаково и получают ошибку сразу, если файл не соответствует ожиданиям.

- Схемы таблиц (`TableSpec`): имя файла, индекс, колонки, типы, допустимость пропусков. `validate(df, spec)` бросает `ContractError` со списком проблем.
- Загрузчики `load_*` в `data/api.py` — **единственный** способ читать данные. Запись — `write_table(df, spec)` (проверяет схему перед записью).
- `python -m marketsim.data.check` — проверка всех файлов и связей между ними.
- Описание таблиц: `docs/plans/phases/F1_data_collection.md`, раздел 6; назначение функций: `src/marketsim/data/README.md`.

## K2. Граф зависимостей и внешние сигналы

**Зачем:** агенты (S) читают граф и сигналы одинаково для синтетики и реальных данных; D2 может перестраивать граф, не трогая симуляцию.

- Граф — папка с `nodes.csv`, `edges.csv`, `meta.json`. Колонки фиксированы (`NODE_COLUMNS`, `EDGE_COLUMNS`).
- Ребро `parent → child`, вес $w$: родитель +1% → оценка ребёнка $+w$%. `w_direct` — для близоруких (только от внешних узлов), `w_full` — для сетевых. Каждое ребро с обоснованием.
- `load_graph`, `save_graph`, `DependencyGraph.validate()` (включая спектральный радиус < 1), `parents(child, mode)`.
- Внешние сигналы: схема `EXTERNAL`, файл `external_<scenario>.parquet` (или `.csv` в `fixtures/`), индекс `session`, по колонке на внешний узел.
- `reference_path(graph, external, mode)` → эталонная траектория по сессиям.
- Подробно: `docs/plans/phases/F2_dependency_graph.md`.

## K3. Лог прогона

**Зачем:** метрики (D1) и визуализация (O, D1) работают с любым прогоном и не зависят от кода симуляции.

- Папка `runs/<run_id>/`: `meta.json` + таблицы `trades`, `orders`, `book`, `signals`, `valuations`, `events` (parquet).
- `load_run(run_dir)` читает и проверяет. `LOG_VERSION` повышается при изменении формата.

## K4. Конфигурация эксперимента

**Зачем:** один YAML описывает эксперимент целиком; runner, метрики и отчёт ссылаются на одну и ту же конфигурацию.

- `base` (поля `RunConfig` фиксированы), `seeds`, `grid` (ключи — пути через точку, например `agents.herding.h`).
- Секция `agents` принадлежит S и свободна по формату: параметры агентов меняются без изменения контракта.
- `load_config`, `expand` (декартово произведение сетки × seeds).

## 7. Как менять контракт

1. Открыть PR с меткой `contract-change`. В описании: что меняется, зачем, кого затрагивает.
2. В **том же PR**: код контракта, тесты в `tests/contracts/`, этот документ, при необходимости `CONTRACT_VERSION` (K1, совпадает в Python и C++) или `LOG_VERSION` (K3).
3. Одобрение **владельца и всех потребителей** из таблицы выше.
4. Добавить новую **необязательную** колонку или функцию — быстрый путь (одобрение владельца, потребителям — уведомление). Переименовать, удалить, изменить тип или смысл — полная процедура.

**Нельзя:** править тест контракта, чтобы прошла своя реализация. Если тест неправ — это изменение контракта по этой процедуре.
