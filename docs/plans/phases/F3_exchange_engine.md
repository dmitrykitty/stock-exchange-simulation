## 0. Что строим

```text
агенты (S) ──place/cancel──► MarketGateway (Python, O) ──submit/cancel──► Exchange
                               портфели, резервирование                 ├─ PyExchange (Python-эталон, O)
                               расчёт обеих сторон сделки               └─ CppExchange → lob_core (C++, O)
```

- **Exchange** — стаканы всех активов и сопоставление заявок. Ничего не знает о деньгах агентов и о времени.
- **MarketGateway** — контроллер между агентами и биржей: проверяет и резервирует ресурсы, отправляет заявку, рассчитывает сделки для обеих сторон, следит за сохранением денег и акций.
- Две реализации Exchange с **одинаковым** поведением: Python-эталон (простой, медленный, правильный) и C++ (быстрый). Одинаковость проверяется дифференциальными тестами.

## 2. Семантика (это и есть спецификация)

### 2.1 Единицы

- Цена — целое число тиков (`int64`), 1 тик = 0,01 USD. `double` в ценах не используется: иначе результат зависит от машины.
- Количество — целое число акций (`int64`).
- Деньги в шлюзе — целые центы (`int64`); 1 тик × 1 акция = 1 цент.
- `NO_PRICE` = минимальный `int64`: пустая сторона стакана / сделок не было.

### 2.2 Заявки

| Поле | Значения |
|---|---|
| `asset` | 0 … n_assets − 1 |
| `owner` | id агента |
| `side` | `BUY = 1`, `SELL = −1` |
| `qty` | > 0 |
| `limit` | > 0; максимальная цена покупки / минимальная цена продажи |
| `tif` | `GTC = 0` (стоит до отмены), `IOC = 1` (исполнить что можно, остаток снять), `GTD = 2` (в стакане как GTC; истечение делает шлюз) |

**Рыночная заявка** = IOC с защитной ценой в `limit`. Отдельного типа нет.

### 2.3 Сопоставление

1. **Price-time priority:** входящая покупка берёт самые дешёвые ask; при одинаковой цене — более раннюю заявку. Для продажи зеркально.
2. Сделка возможна, если `bid ≥ ask`. **Цена сделки — цена заявки, которая стояла в стакане (maker).**
3. Количество сделки — минимум остатков. Полностью исполненные заявки удаляются, процесс продолжается, пока входящая не исполнена или цены не перестали пересекаться.
4. Остаток GTC/GTD встаёт в стакан в конец очереди своей цены. Остаток IOC снимается.
5. **Self-trade:** если на противоположной стороне есть заявка **того же владельца** по цене, с которой входящая могла бы сопоставиться (для покупки: свой ask ≤ limit), входящая заявка **отклоняется целиком** (`REJECTED_SELF_TRADE`) **до** любых изменений состояния.
6. **Неверная заявка** (`qty ≤ 0`, `side ∉ {1, −1}`, `asset` вне диапазона, `limit ≤ 0`) → `REJECTED_INVALID`, состояние не меняется.
7. **`order_id`** выдаётся каждой поданной заявке, включая отклонённые: 1, 2, 3, …
8. **`seq` сделок** — 1, 2, 3, … общий счётчик для всех активов.
9. **`submit_batch`** даёт ровно тот же результат, что последовательные `submit`.

### 2.4 Статусы отчёта

| Статус | Код | Когда |
|---|---|---|
| `RESTING` | 0 | ничего не исполнилось, заявка в стакане |
| `FILLED` | 1 | исполнена полностью |
| `PARTIAL_RESTING` | 2 | часть исполнена, остаток в стакане |
| `PARTIAL_CANCELLED` | 3 | IOC: часть исполнена, остаток снят |
| `CANCELLED_IOC` | 4 | IOC: ничего не исполнилось |
| `REJECTED_SELF_TRADE` | 10 | п. 5 |
| `REJECTED_FUNDS` | 11 | только шлюз: не хватает денег или акций |
| `REJECTED_INVALID` | 12 | п. 6 |

`avg_price` — средняя цена исполнения в тиках (NaN, если ничего не исполнилось).

### 2.5 Пример (из тестов)

В стакане два ask: A — 5 шт. по 101, B — 5 шт. по 102. Приходит покупка IOC 8 шт. с limit 103 → сделки 5 × 101 (с A) и 3 × 102 (с B); `avg_price` = (5·101 + 3·102)/8 = 101,375; статус `FILLED`; в стакане остаётся ask 2 шт. по 102.

### 2.6 Шлюз: резервирование и расчёт

- Покупка резервирует `qty × limit` центов; продажа — `qty` акций. Не хватает → `REJECTED_FUNDS`, стакан не трогается.
- После сделки по цене ниже лимита излишек резерва **сразу** возвращается в доступные деньги.
- Сделка меняет портфели **обеих** сторон: у taker сразу, у maker — по его зарезервированной заявке.
- `cancel` (только свою заявку; чужую — `ValueError`) и `expire` возвращают снятый остаток и освобождают **только оставшийся** резерв. `expire` для уже исполненной заявки ничего не меняет.
- Инварианты (`check_invariants`): сумма денег всех агентов и сумма акций каждого актива постоянны; никакой ресурс не отрицателен.
- `drain_fills()` отдаёт сделки с прошлого вызова — для записи лога (K3).

**Пример (тест `test_reservation_partial_fill_and_release`):** у агента 2000,00 \$ (200 000 центов). Покупка 10 шт. с limit 102,00 → резерв 102 000. Исполнилось 6 шт. по 100,00 → заплачено 60 000, излишек 6 × 200 = 1200 вернулся. Доступно 99 200, в резерве 40 800 (под оставшиеся 4 шт.). После отмены: доступно 140 000, резерв 0.

### Шаг 2 (неделя 1, дни 3–5). `PyExchange`

Цель — **правильность и простота**, не скорость. Предлагаемые структуры:
- на каждый актив две стороны; сторона = `dict[price → deque[order]]` + отсортированный список цен (`bisect`) или `heapq`;
- `dict[order_id → order]` для отмены;
- счётчики `next_order_id`, `next_seq`, `last_trade[asset]`.

Псевдокод `submit`:

```text
order_id = next_order_id++
if invalid(order): return REJECTED_INVALID
if self_trade_possible(order): return REJECTED_SELF_TRADE           # до изменений!
while order.qty > 0 and opposite side not empty and crosses(order.limit, best opposite price):
    maker = first order at best opposite price
    q = min(order.qty, maker.qty); record fill(seq=next_seq++, price=maker.price, q)
    reduce both; remove maker if empty
status/rest by tif (GTC/GTD -> rest remainder, IOC -> cancel remainder)
```

**Готово, когда:** `pytest tests/contracts/test_market_contract.py -k python` — все тесты проходят (сейчас 18 пропускаются).

## 4.1 Скорость (29.10.2026)

`python benchmarks/bench_exchange.py`: 200 000 случайных заявок, 18 активов, ноутбук разработчика.

| Как вызываем | Сначала (результаты через списки объектов) | После перехода на буферы |
|---|---|---|
| `PyExchange`, по одной | ~101 000 | ~106 000 |
| `CppExchange`, по одной | ~122 000 | ~148 000 |
| `CppExchange`, пачками по 100 | ~208 000 | **~1 920 000** |
| `CppExchange`, пачками по 1000 | ~222 000 | **~2 420 000** |
| `lob_core` напрямую, с Python-объектами | ~1 670 000 | ~1 260 000 |

**Как сделано:** C++ пишет результаты в один непрерывный буфер упакованных записей с той же побайтовой раскладкой, что у `FILL_DTYPE`, `REPORT_DTYPE`, `DEPTH_DTYPE`; numpy получает буфер без копирования и читает его через `.view(dtype)`. Пачка заявок на вход передаётся так же. При импорте адаптер сверяет раскладку записей C++ (`lob_core.WIRE_LAYOUT`) с dtype контракта и отказывается загружаться при расхождении. Контракт K1 не изменился.

**Выводы:**
- пакетный путь в ~23 раза быстрее Python-эталона;
- поштучный вызов (~150 000 в секунду) упирается в накладные расходы Python на каждый вызов. Если симуляции понадобится скорость, агенты должны отправлять решения пачками. Для этого шлюзу нужен `place_batch` — вопрос к S при согласовании K1;
- следующее возможное узкое место — расчёт сделок в шлюзе (Python, цикл по сделкам). Мерить после того, как появится симуляция (F4).
